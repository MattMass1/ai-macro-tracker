# ADR-001: Food agent v1 orchestration and contracts

Status: accepted for the local v1 build (branch `claude/food-agent-v1`). Not pushed, deployed, migrated or enabled.
Date: 2026-11-02. Author: WP2 writer (Opus). Brief: DevOps `mmmacros-agent-build/AGENT.md` sections 4, 5, 8. Plan: `docs/agent/PLAN.md`.

## Context

The food agent must turn a chat message into a draft, show a preview, commit only on the user's own unambiguous "yes" to that exact preview, write once, read the saved row back and build the receipt from it. Three real failures drive the design:

1. "ahi tuna bowl again, the one I had last time" copied an unrelated recent entry.
2. "Half a quarter pounder" then "with cheese" logged the whole 520 kcal panel with "half" in the name.
3. "yes but 6 oz instead of 12" re-searched with "6 oz" in the query and re-asked four times.

What the repo already has (read in code, not assumed):

- Turn boundary `CanvasService.turn` (`server/src/agent_canvas.py:655`), model injected as `agent=` so tests script it offline.
- Owner-scoped revisioned drafts (migration 004): `Store.save_meal_draft` is a revision CAS; `meal_drafts.pending_question` is TEXT up to 1000 chars; `meal_draft_items.resolution` and `field_origins` are JSONB.
- `Store.commit_meal_draft(draft_id, expected_revision, request_hash, values, component_metadata)` commits through `run_idempotent` with key `meal-draft:{id}:{rev}`, re-checks `state='ready'` and the revision under a row lock, and `_guard_unknown_nutrients` runs before writes. `Store.fetch_entry_revision` reads the saved row back.
- `nutrition_entries` has no identity or portion columns; `component_metadata` JSONB on the row can carry them.

Environment facts for this run: Pydantic 2.14.2 is in the venv. `langgraph` and `langchain` are **not** installed, and this run may not install packages, so LangGraph could not be prototyped or tested offline here. Everything below about LangGraph is from its documented design, not from running it.

## Decision 1: orchestration framework (time-boxed comparison)

| Criterion | (a) App-owned coordinator + Pydantic v2 | (b) LangGraph |
|---|---|---|
| State store | The existing migration-004 draft tables with revision CAS. One source of truth. | A checkpointer (Postgres saver or similar) holds graph state. That is a **second state store** beside `meal_drafts`, which must be kept consistent with it, plus its own tables (a migration). |
| Agent loop | One structured model call per turn, then plain Python. | LangGraph runs its own node/edge loop; the canvas already has a loop in `CanvasService.turn`. Two loops stacked, which the brief forbids. |
| Idempotent commit | `commit_meal_draft` + `run_idempotent` as is. | Same store call inside a node; graph replay/retry semantics add a second retry layer to reason about. |
| Confirmation authority | Code reads the user's message and the stored `PendingConfirm`. | Same check would still be custom code inside a node; LangGraph's interrupt/resume is a UI-pause mechanism, not an authorization check. |
| Offline testability | Scripted `agent=` plus fake store; proven pattern in 50+ existing test files. | Not testable here at all (not installed). Would need a fake checkpointer too. |
| Dependencies | `pydantic` only (already a transitive dependency of `fastmcp`; now pinned directly). | `langgraph`, `langchain-core` and their transitive tree; new upgrade surface on a server with 1 maintainer. |
| Latency | One model call per normal turn. | Same model calls plus checkpoint writes per node. |
| What it would buy | n/a | Visual graph, built-in human-in-the-loop pause. Neither is needed: the draft row already is the pause, and the flow has five fixed steps. |

**Decision: (a) small app-owned coordinator + Pydantic v2.** LangGraph is not clearly simpler, would add a second state store and a second agent loop, and is not testable offline in this run. Revisit only if the flow grows beyond a fixed draft, preview, confirm, commit, readback sequence.

## Decision 2: where it lives and how it is gated

- Package `server/src/food_agent/` (`contracts.py`, `portion.py` now; `coordinator.py`, `confirm.py`, `find_food.py`, `recall.py` in later WPs).
- Gate in `release_gates.py` (WP6): `FOOD_AGENT_ENABLED` must equal exactly `true`; optional `FOOD_AGENT_USER_IDS` canary list of user UUIDs (a malformed list closes the gate); and the live 004 draft schema must be present. With the gate off, `CanvasService.turn` is byte-for-byte the old path, proven by a test.
- Turns the model classifies as `not_food` are handed to the existing canvas/coach path unchanged. Workouts keep their current path.

## Decision 3: typed contracts (WP2, this ADR's code)

`server/src/food_agent/contracts.py`, all Pydantic v2 models with `extra="forbid", strict=True, frozen=True`:

- The model returns `AgentTurn{schema_version="food-agent/1", actions: 1..8}`; `AgentAction` is a union discriminated on `type`: `add_items`, `revise_item`, `remove_item`, `recall_meal`, `confirm`, `cancel`, `ask`, `not_food`.
- Identity (`FoodIdentity`), portion (`Portion`) and modifications (`Modification`) are separate types and separate fields everywhere. `revise_item` fields that are omitted or null mean **preserve**, so "with cheese" revises identity and keeps portion 0.5 (failure 2), and "6 oz instead of 12" revises only portion (failure 3).
- "Last time" is a `recall_meal` action against the user's own history (failure 1); the model cannot name an entry id to copy.
- The model never supplies nutrients, SQL, user ids or a `confirmed` flag: those keys are rejected, not ignored. `confirm` carries only `draft_ref` and `shown_revision` and is a hint, never authority. A turn cannot mix `confirm` with edits, and `not_food` must be alone.
- `agent_turn_json_schema()` emits a schema for OpenAI strict structured outputs (object root, every property required with nullable optionals, `additionalProperties: false` everywhere, union as nested `anyOf`). Length/range limits are enforced by Pydantic on parse, not in the schema.
- Portion math is pure (`portion.py`): fractions of a serving always work; a bare "oz" against a fluid-ounce serving is fluid ounces; mass against volume with no density is `None` (ask); unspecified is one serving only when the source defines one. Unknown nutrients stay `None` through scaling and totals.

## Decision 4: reuse, not rewrite

- Draft persistence: `Store.save_meal_draft` (CAS) and the 004 item table. `DraftItemState` (identity, portion, modifications, resolved candidate, multiplier) is stored in `meal_draft_items.resolution` JSONB.
- Commit: `Store.commit_meal_draft` (idempotent by `meal-draft:{id}:{rev}`); readback: `Store.fetch_entry_revision`; receipt: `Receipt.from_saved_row`, never the draft.
- Saved row: identity, portion, modifications and the list of unknown nutrients go in `component_metadata` so the receipt can show unknown as unknown even where a column defaults to 0.
- The new path never calls `MealDrafts.handle`/`settle` auto-commit (`meal_drafts.py:394`), which is the confirmation gap.

## Decision 5: confirmation authority

- A commit happens only when **code** detects an unambiguous affirmation in the user's own message, exactly one open preview exists for that owner, and the stored `PendingConfirm{draft_id, revision, content_hash}` still matches the draft's current revision and recomputed `content_hash(items)`. The model's `confirm` action can never commit on its own, and a model cannot express `confirmed=true`.
- `content_hash` is a canonical sha256 over identity, portion (kind, amount, unit), modifications, resolved food id and multiplier; independent of key and item order; excludes display wording.
- Note for WP3: `save_meal_draft` increments the revision, so writing the binding into `pending_question` itself bumps the revision. The coordinator must store the revision that the CAS will produce (expected + 1) or re-read after the write; it must not bind to the pre-write revision.
- Outcomes use `ToolOutcome{status, effect, safe_message}`. A lost commit response or failed readback is `effect="unknown"` ("could not verify it saved") and is reconciled by the same operation key, never reported as failure and never retried as a new write.

## Decision 6: no new migration

The preview binding lives in `meal_drafts.pending_question` as compact JSON (about 160 characters, limit 1000; plain-text questions parse as "no binding"). Identity, portion and modifications live in `meal_draft_items.resolution` JSONB and in the saved row's `component_metadata`. WP7 adds a migration only if WP3 to WP5 prove a table is required.

## Decision 7: latency budget

One structured model call per normal turn (strict JSON schema). Food lookups are code tool calls behind the existing caches. A bounded second model call is allowed only to choose between close candidates. Recall is one owner-scoped SQL query. Confirmation ("yes") needs no model call when code detects the affirmation and the binding matches.

## Consequences

- Positive: one state store, one loop, reuse of the tested CAS/idempotency/readback code, strict typed boundary that makes the three real failures structurally hard to repeat.
- Negative: we own the coordinator (small, fixed flow). No graph visualization. The model sees a strict schema, so a provider without strict structured outputs needs a parse-and-reject fallback (Pydantic still validates).
- Open: `nutrition_entries.calories` is `NOT NULL DEFAULT 0` and the other macro columns default to 0. Unknown nutrients must be recorded in `component_metadata` at commit (WP3) for `Receipt.from_saved_row(..., unknown_nutrients=...)` to keep them unknown.
