## 1. What the product is (one paragraph)

Macro Coach / MMMacros: a multi-user iPhone app with an AI coach. A lifter types or speaks what
they ate ("3 eggs and a blueberry bagel", "half a quarter pounder", "the tuna bowl I had last
Thursday"); the agent figures out the food, the portion, finds real nutrition data, shows a
one-line preview, and logs it on "yes". Headline promise: **fastest accurate logging**. Protein is
the headline number. Matthew (production user id `be6333cc-e4c1-48f2-adb1-5e7f14dbf7c2`) is user #1
and the bench is built from his real chats. **Matthew's data is never deleted. Ever.**

## 4. Decisions already made (do not re-ask these)

From `SPEC.md`, decided by Matthew:

| Decision | Value |
|---|---|
| Buyer | Lifters tracking macros; Matthew is user #1 |
| The one promise | Fastest **accurate** logging by voice/text |
| v1 scope | Food only. Workouts are a later agent (plan-only, suggest-not-set), gated on food hitting 90% |
| Confident items | Show a draft first; one tap or a typed/spoken "yes" commits. No extra questions when confident |
| Personality | Brief. Coach only when asked. Receipts are built from the saved row, not model prose |
| Data source routing | **Route by kind, in code.** generic/homemade -> curated table -> USDA FDC -> CoFID; restaurant/packaged -> FatSecret with brand agreement; anything else or any miss -> web estimate marked "est.". FatSecret never sees a whole-food query. **No lane asks "which one"; each returns its top compatible match as "matched to X".** |
| Ship gate | 90%+ cases right food AND right portion on the real-chat replay bench (decided), plus proposed hard rules: 0 receipt/row mismatches, p50 < 3 s and p95 < 6 s on known foods, no failure class worse than the old app |
| Memory | Nightly pattern review suggests usuals; nothing learned without a tap; never edits logged meals |
| Voice | Log now, ask later (labeled guesses, follow-up cards) |
| Framework | App-owned coordinator + Pydantic v2, NOT LangGraph (ADR-001); one state store (the 004 draft tables) |
| Own MCP / separate router agent | No. One in-backend `find_food` service; routing from the interpreter's `kind` validated by code |

Matthew's UX rules for food logging (each was a complaint; these are hard requirements):

1. The user named the product: use the closest real product and SAY which ("matched to X") in the
   receipt. **Never** "Light or Regular?", never a numbered variant list, never "Did you mean X?".
2. Never ask for something the source knows (grams per serving, macros).
3. "Half a serving" = 0.5 x the source serving; fractions must always work.
4. Never re-ask an amount already given.
5. Ask raw/cooked only for a *weighed* food whose weight changes with cooking.
6. Never ask for a brand or dish name. A brand already in the user's words is known; do not ask "where was it from".
7. One question per reply, asked **once**. If unanswered on a later turn, do not ask again: log what is
   ready, name what was not counted ("tell me what it was to add it").
8. Partial logging: ready foods commit now; an unknown food never blocks the meal.
9. Every food ends in exactly one of: **verified** / **estimated** (auto-added, marked "est." with its
   source, removable) / **not counted** (named in the receipt) / **asked once**.
10. Replies are short. "Logged X: 31 g protein, 280 kcal, ..." built from the saved row.

## 5. What exists and is reusable vs. what is broken

### Reuse as-is (tested, reviewed)

- **Store + schema.** `Store.commit_meal_draft(draft_id, expected_revision, request_hash, values, component_metadata)`
  commits through `run_idempotent` keyed `meal-draft:{id}:{rev}`, re-checks `state='ready'` under a row lock.
  `Store.fetch_entry_revision(entry_id)` reads the saved row back. `save_meal_draft` is a revision CAS.
  Tenant scoping via `current_user_id()` bound from the bearer token. Cross-user child rows are rejected by
  the DB (composite FKs). Do not add a second state store.
- **Source adapters.** `usda_lookup.py` (FDC POST search, `select`, `compatible`, `for_portion`, household
  measures), `food_lookup.search_fatsecret` / `fatsecret_name_options`, `web_nutrition_lookup.lookup`
  (Exa or OpenAI web_search, labeled estimate), `cofid_lookup`, `generic_foods` (curated rows with FDC ids),
  `dish_estimates.py` (typical recipes from pinned USDA rows, declares raw/cooked `basis`).
- **Portion math.** `food_agent/portion.py` (`multiplier(portion, serving_basis, identity)`): fractions,
  mass vs volume, fl oz vs oz, unknown nutrients stay `None`. Pure, 500 lines of tests behind it.
- **Typed contracts.** `food_agent/contracts.py`: `FoodIdentity{name, brand, variant, kind, preparation}`,
  `Portion{kind, amount, unit, text}`, `Modification`, strict JSON schema for OpenAI structured outputs.
  Reusable shapes; you may redesign the action union.
- **Release gating pattern.** `release_gates.py` exact-`true` + canary UUID list; tests prove the old path is
  byte-for-byte unchanged with the gate off.
- **Bench harness.** `scripts/food_agent_bench.py --lane A|B|C`; lane C counts every wire attempt, reserves
  dollars from a versioned rate card before each call, hard caps ($10 / 300 model calls / 200 lookups),
  zero-tolerance counters (false "logged", duplicates, stale commits, cross-tenant, commit-before-confirm).
  Scorer needs `expected_nutrients` gold on cases to score strict; today labels lack it, so strict
  identity/portion are what is measured.

### Broken: the agent/orchestration layer (replace)

- `food_agent/coordinator.py` (862 lines) + `find_food.py` (566) + `model_adapter.py` + `recall.py`.
  Measured behavior in section 6. Structural problems:
  - **Refusal with no exit.** `find_food._identity_check` returns `variant`/`brand`/`cook` -> `no_match`; the
    closest-option fallback only accepts "cosmetic" differences, so real near matches are refused; the
    coordinator then emits a fixed code-authored question (`coordinator.py:749`:
    `"I couldn't find {X}. Where was it from?"`) every turn with no state change. 19/26 live runs ended there.
  - **Lanes refuse but do not resolve.** The generic lane correctly refuses FatSecret for "3 eggs", but USDA
    `compatible()` + FNDDS/SR rows did not yield an acceptable row and the web fallback result was never
    accepted (47 web calls, 0 accepted), so plain foods go unlogged.
  - **User-supplied numbers ignored** (pasted label, "I'd say 325 calories").
  - **Model-authored `ask` is unbounded**: the interpreter asks about things it should draft.
  - **Two overlapping engines** (`meal_drafts.py` legacy path + `food_agent`) with different rules; the
    not-food classifier can hand a mid-draft "yes" to the old path.
- `agent_canvas.py` (2259 lines) mixes canvas rendering, setup approvals, workout plan previews and the
  chat turn. The new layer should plug in at `CanvasService.turn` via the existing `food_agent_factory`
  seam (or an equivalent single seam) and not grow this file.

**Failure classes to design out** (each with a real transcript behind it):

1. **Dead-end loop.** "Chic fil a Grilled chicken club sandwich" -> "I couldn't find Chick-fil-A Grilled
   Chicken Club Sandwich. Where was it from?" repeated for 9 turns including after the user said
   "USE THE INTERNET". FatSecret had "Grilled Chicken Club w/ American"; brand was in the user's words.
2. **Near-match refused.** "Barebells Marshmallow Peanut Road" (FatSecret: "Marshmallow Rocky Road") ->
   refused. "Taco Bell Chipotle Crunchwrap slider" (FatSecret: "Creamy Chipotle Crispy Chicken Crunchwrap
   Slider") -> refused. Required behavior: match to the closest real product, disclose the difference,
   log on yes.
3. **Plain foods unresolved.** "3 sunny side up eggs" / "3 eggs" -> nothing. "1 blueberry bagel" ->
   "where was it from?". "sourdough toast" -> nothing. Generic lane must resolve common foods from USDA
   (FNDDS has cooked forms: "Egg, whole, fried", "Bagel, with raisins"...), then curated rows, then web.
4. **Variant lists** (old build): "Was it the X or the Y?" / "Did you mean X?". Rule 1 above.
5. **User-supplied nutrition ignored.** "I'd say 325" (calories), a pasted label table (520 kcal, 22 g fat,
   44 g carbs, 37 g protein) -> asked a question instead of using the numbers.
6. **Re-asking a confirmed item / amount** ("3 eggs" after "3 sunny side up eggs"; "1 serving" after "1 piece").
7. **Historical recall miss.** "the ahi tuna bowl I had last Thursday" -> "couldn't find in the last 4 months"
   (the fixture has it; recall query matching is too strict or the date hint is ignored).
8. **Mid-draft handoff to the old path** on "Yes" / "Do 1 slice" (not-food classifier fires inside an open draft).
9. **Lookup fan-out.** Up to 14 provider calls in one turn; 200 lookups cover ~26 runs. Needs per-turn
   memoization and a per-turn cap so a full bench fits the budget.
10. **p95 latency 15-20 s** on lookup-heavy turns (web_search is 8-12 s). Show progress or parallelize; never
    let a slow web call block the preview of items that already resolved.

## 7. What the new layer must do (acceptance)

Functional:

- One package `server/src/<new_name>/` behind a new exact-`true` gate in `release_gates.py` + optional canary
  UUID list. With the gate off, `CanvasService.turn` is byte-for-byte the old path (test it).
- One structured model call per normal turn: the model returns identity/portion/modifications/intent as
  typed JSON (never nutrients, never ids it was not given). Code does lookup, routing, portion math,
  preview, confirm detection, write, readback, receipt.
- Source routing by kind in code (section 4), **and every lane resolves or estimates**: a lane that finds no
  exact row returns the closest compatible candidate with the difference disclosed, or a labeled estimate,
  or "not counted" with a reason. Never a dead end; never the same question twice.
- Hard identity guards stay: preparation (raw vs cooked), species, lean/fat ratio, explicit flavor/variant
  the user stated are never silently swapped. Everything else is "matched to X" with disclosure.
- User-supplied nutrition (typed or pasted label) is used, labeled as user-supplied, and wins over a lookup.
- Recall ("last Thursday", "my usual", "same as last time") is one tenant-scoped SQL query against the
  user's own entries; a recent unrelated meal is never a fallback.
- Confirmation authority is code: commit only on an unambiguous affirmation in the user's own words bound
  to the exact preview revision/content hash (keep the `PendingConfirm` idea from ADR-001).
- Writes: `Store.commit_meal_draft` (idempotent), readback via `fetch_entry_revision`, receipt from the saved
  row. Failed readback = "unverified", reconcile by key, never re-send.
- Amendments never silently drop food the entry already counts (only the user's remove/skip does).
- Voice channel: same agent, "ask later" setting (labeled guesses, follow-up later). Can be v1.1.

Bench gate (lane C, real model + real lookups, 20 cases x 2, same caps):

1. **>= 90% of case runs** log the right food AND right portion (strict identity + portion; add
   `expected_nutrients` gold to labels so strict nutrition can be scored too).
2. Zero-tolerance counters all 0.
3. Turn latency p50 < 3 s, p95 < 6 s on known foods (measured on passing turns).
4. No failure class worse than the old app (wrong past meal, lost fraction, re-asked confirmed item).
5. Questions per run <= old app (1.65).

## 8. Suggested shape (not binding; proposed by the previous orchestrator)

```
server/src/food_agent2/            (name it; keep food_agent/ untouched until the switch)
  gate.py          exact-true flag + canary list (copy release_gates pattern)
  contracts.py     reuse FoodIdentity/Portion/Modification; new Turn/Action union
  interpret.py     one strict-JSON Responses call; model never asks, it emits needs: amount|basis|none
  resolve.py       the ONE find_food(identity, portion, user) -> Candidate | Estimate | NotCounted
                   order: user history/usuals -> lane by kind -> closest compatible -> labeled estimate
                   per-turn memo, parallel per item, hard per-turn call cap
  disclose.py      "matched to X (you said Y)" text from identity diff
  draft.py         draft state over the 004 tables (reuse Store CRUD), one open draft per user/session
  confirm.py       affirmation detection + PendingConfirm binding (port from food_agent/confirm.py)
  commit.py        commit_meal_draft + readback + Receipt.from_saved_row
  turn.py          the coordinator: interpret -> apply -> resolve -> preview|commit -> reply
  wiring in agent_canvas.CanvasService via the existing food_agent_factory seam
```

Keep the model's job small: identity + portion + modifications + which open item a message refers to.
Everything else is code and is unit-tested with whole-dialogue replays (real coordinator, in-memory
store, fake providers), the pattern in `tests/test_meal_flow_v2.py` and `tests/test_food_agent_flow.py`.

## 10. Cost/latency facts for the design

- Interpreter `gpt-6.1-terra`: ~2.3 s p50 per call, 1.8-2 k prompt tokens with context. Price card in the
  bench harness (`food_agent_budget.RateCard`).
- Web fallback (`gpt-5.6-luna` + hosted web_search): 8-12 s, ~13 k prompt tokens, ~$0.04 reserved per call.
  Never on the critical path of a preview for items that already resolved.
- USDA FDC: free, 1000 req/hour/key, CC0 (cache forever). FatSecret Basic: free, 5000/day, attribution
  required, panels may not be persisted (`cache_allowed=False`): keep identity, refetch at commit.
- The 200-lookup cap is the binding constraint on the bench; the new resolver must average well under
  5 provider calls per case to finish 40 runs.
